# Walder — manual QA checklist

The one checklist for a human at the keyboard. It replaces `docs/archive/QA-M3.md`
(kept for its history) and folds in the data layer and the behaviour work.

Everything not listed here is covered by `npm test` and `npm run typecheck`.

## Before you start

Run the app one of two ways:

- **A real install** — the `.dmg` or the `.exe`. This is the one that matters:
  it is what you will actually use, and a few checks (Launch at login, the
  installers, Gatekeeper) only exist there.
- **From the project folder** — `npm run dev`. Faster to repeat, and it is the
  only way to reach the **fake-data** items under **Developer ▸** (Inject usage,
  Simulate account state, Simulate hook, Toggle fullscreen mode), which is how the
  faces, the barks, the account states, the hook reactions and the fullscreen
  sleep are triggered on demand instead of waited for. **Simulate account state**
  lays one row over every poll until you pick **Normal** or quit: Codex credits
  left or at 0 (out of credit), Extra usage at 85 % or at its spend limit with no
  cap, or 455 % over the Codex credit limit. It is memory only: nothing simulated
  is written to the settings file. The bark memory is not saved while it is on,
  and picking **Normal** puts back the bark memory from before the first simulated
  state, so nothing he barked or noted about a fake state is remembered after it.
  They are deliberately missing from a real install: a mascot that
  can be *told* to say "100 % used" is a mascot nobody can trust.

**Verbose log** (in the Walder window, Advanced page) works in a real install too,
because it is the only way to produce a diagnosable record of an intermittent
fault. Tick it before reproducing anything odd; **Reveal log file** in the menu
shows the file. Since 2026-11-17 the whole **Developer ▸** menu is missing from
a real install (set `WALDER_DEV=1` to bring it back).

Useful while testing:

```
WALDER_LOG=1 npm run dev                  # print diagnostics as you go
WALDER_DEBUG=1 WALDER_LOG=1 npm run dev   # also outline the clickable area in magenta
```

Quit between checks with **Quit** in the menu, never by closing something:
Walder deliberately never quits on his own.

## How to fill this in

Tick the platform you tested on, and write pass / fail / not tested in **Result**.

| Mark | Meaning |
| --- | --- |
| ⚠ | **Not verified by builders**, for a reason beyond the two below. Nobody has ever seen this work. The reasons are listed at the end |

Two blanket caveats apply to **every** row in this file, so they are not repeated
per line:

- **Until 2026-10-01 no builder had seen Walder on a screen.** Screen capture
  was not available in the early build sessions. Since the 0.2.8 QA loop
  (2026-10-01 onwards) rows have been checked on screen by the loop and by the
  owner, as each Result says: a ☑ was seen, a ☐ was not, and a ⚠ row's reason
  in the table at the end says what was out when it was written.
- **Windows was first run on 2026-10-02/03** (one 1920×1200 display at 100 %,
  Windows 11), in the loop recorded in `docs/handoffs/QA_0.2.8_WINDOWS_REPORT.md`.
  The **Windows** column now reads from that pass; "Windows: out" marks the
  hardware and account states that machine could not produce, and the rows
  left ☐ without a Windows note are the owner's sitting.

### Known behaviour in §6, not faults

- **A maximised window with the Dock hidden reads as fullscreen.** macOS reports
  a fullscreen window at the display's full width, sitting on its bottom edge and
  starting 33 px down (the hidden menu bar keeps its strip) — and with the Dock
  hidden too, a merely *maximised* window is reported at exactly those numbers.
  Nothing in the geometry separates them, so Walder sleeps for both. Accepted
  deliberately: with the Dock hidden and a window filling the screen the owner is
  effectively fullscreen anyway, and the stricter rule that was in place until
  2026-09-08 missed every in-browser video there is. With the Dock visible (the
  default) a maximised window is 66 px short at the bottom and he stays up.
- **On Windows an ordinary maximised window no longer reads as fullscreen** when
  no taskbar is reserved on that display (taskbar auto-hide, or a second monitor
  without a taskbar). Until 2026-11-16 it did, and he slept under every maximised
  window. A maximised window sticks out past all four display edges by its
  resize border (8 px at 100 %, 8–10 px at 125 %, measured) and a fullscreen one
  sits exactly on the display; that is now the test (audit W6). Seen on screen at
  100 % and 125 % with auto-hide on, uncommitted at the time; the second-monitor
  case is reckoned, not seen. A restored window that is exactly display-sized
  still reads as fullscreen.
- **On Windows a shell surface over a film keeps him asleep, for up to 15 s.**
  The tray overflow flyout, the taskbar, Alt+Tab / Task View, Start, Search,
  Quick Settings, the notification centre and Widgets sit on top of the film
  without ending it, so while one of them is the foreground window the state he
  was in is held (audit finding M5, 2026-11; before that, about four seconds of
  the flyout woke him over a film that was still playing). The hold is bounded
  because the foreground can *land* on the taskbar when the player closes: then
  he wakes about 15 s + 4 s later without anything being touched. Win+D (the
  real desktop, `Progman`/`WorkerW`) and a File Explorer folder window still wake
  him after the usual two polls. Confirmed on screen on Windows 11 build 26200
  (2026-11-14), foreground class and owner process per surface:

  | Surface | Class | Owner |
  |---|---|---|
  | Taskbar | `Shell_TrayWnd` | explorer |
  | Tray overflow (Win+B, Enter) | `TopLevelWindowForOverflowXamlIsland` | explorer |
  | Alt+Tab, Task View | `XamlExplorerHostIslandWindow` / `ForegroundStaging` | explorer |
  | Start, Search | `Windows.UI.Core.CoreWindow` | SearchHost |
  | Quick Settings | `ControlCenterWindow` | ShellHost |
  | Notification centre | `Windows.UI.Core.CoreWindow` | ShellExperienceHost |
  | Widgets (Win+W) | `WindowsDashboard` | WidgetBoard |

  Widgets was the one miss of that pass (`fullscreen left` after about four
  seconds) and is held since M5b. The Verbose log names each surface once per
  hold, as it appears — `a shell surface (<class>; owner <owner>) is in front` —
  so Win+B then Enter gives one line for the taskbar and one for the flyout. The
  log redactor masks any unbroken run of 20+ letters, so a long class or owner
  (`Start Menu Experience Host`) is printed with a space between its words: `Top Level Window For Overflow Xaml Island` is
  `TopLevelWindowForOverflowXamlIsland`, `Xaml Explorer Host Island Window` is
  `XamlExplorerHostIslandWindow`. Only classes and owners on Walder's own list
  are ever printed; a shell host's window with a class not on the list shows as
  `an unlisted class of N characters`, so reading a new class needs a separate
  tool, not the log. An explorer window whose class is not on the list keeps
  the old behaviour and wakes him after the usual two polls, which is the safe
  direction; a window of a listed shell host (the Owner column) is held
  whatever its class, for the same 15 s at most.
- **On Windows the fullscreen helper measures in physical pixels** (audit M3,
  2026-11). `powershell.exe` 5.1 is DPI-unaware, so it used to see 96-DPI
  logical rects: right on one display at any scale, wrong on mixed-scale layouts
  where Windows and Electron place a monitor at different coordinates (a 100 %
  monitor right of a 150 % primary). The helper now switches itself to
  per-monitor awareness and the app maps its rects into Electron's units through
  the monitor the window is on (`src/main/win-dpi.ts`). A window that spans two
  monitors of different scale is mapped with the scale of the one Windows says
  it is on, so it is exact there and approximate on the other. A shell surface
  (the hold above) is held by its window class even when its rect cannot be
  placed on any display, so the two fixes do not undo each other.
- **He can take about four seconds to react**, by design: two agreeing 2 s polls.
  During a Space switch macOS reports nothing readable for roughly three seconds,
  and the watch deliberately holds the state it last knew for up to ten seconds
  rather than flapping.
