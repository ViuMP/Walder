## a) The hover card is drawn over the right-click (bone) menu
**Still present on 0.3.0:** yes (from the code).

**Root cause:**
- The `CH.menuOpen` handler (`src/main/ipc-bridge.ts:211-221`) calls `tray.openMenu()` without first calling `getPanel()?.hoverLeave()`. `dragStart` does call it (`ipc-bridge.ts:184`).
- The card window sits at the `screen-saver` level (`src/main/hover-panel.ts:252`, again at `:420`). That level is above the native context menu.
- Hiding the card once is not enough. While the cursor stays on the dog, the renderer sends a `hover:enter` every time the ink rect changes, which is every blink or wag frame (`src/renderer/overlay.ts:1354`). `hoverEnter` re-arms a 250 ms timer (`hover-panel.ts`, the `showTimer` block), so the card would come back over the open menu. One caveat: on macOS `popUpContextMenu` may run a modal tracking loop that holds IPC back until the menu closes. I did not check that, so plan for the re-arm.

**Proposed fix:**
1. In the `menuOpen` handler, call `getPanel()?.hoverLeave()` before `tray.openMenu()`.
2. Add a small `suppress(on)` flag to `HoverPanel`. While it is set, `hoverEnter` does nothing. Set it in `menuOpen` and clear it on the menu's `menu-will-close` event (in `tray.ts` `openMenu`, `menu.once('menu-will-close', …)`), or by a callback passed in.
3. Add a test in `test/ipc-bridge.test.ts` and one in `test/hover-panel.test.ts`.

**Risk:** low. If the clear is ever missed, the card stops appearing until the next menu close or relaunch, so clear the flag in a `finally`-style path as well.

**On-screen check (Mac, then PC):**
1. Hover the dog until the card shows.
2. Right-click the dog (or click the bone) and keep the menu open for 5 s or more while the dog blinks or wags.
3. Pass: no card over or beside the menu at any moment.
4. Close the menu with Esc while the cursor is still on the dog. The card comes back within about 0.25 s of the next pointer movement.
5. Repeat with the tray icon click. Nothing should change there.

## b) Chrome window-fullscreen with its toolbar showing is not detected
**Still present on 0.3.0:** yes (from the code). The rule is unchanged: `coversDisplayAllowingMenuBar` (`src/core/fullscreen.ts:486-499`) accepts a top edge no lower than `display.y + 44` (`MENU_BAR_MAX_PX`, `:50`).

**Root cause:**
- The only record is "content window 996 px high" (`docs/handoffs/QA_0.2.8_REPORT.md:28`). On the 1728×1117 test display that puts the top at about y=121: 33 menu bar plus about 88 of tabs and toolbar.
- That is well past the 44 px allowance, so the window reads as an ordinary window.
- **Not recorded:** the full rect (x, y, width, bottom) and which window `openWindows()` reports for that state. No fixture exists in `test/fullscreen.test.ts`; its Chrome fixtures at `:261-268` are player-fullscreen only.

**Proposed fix:**
1. **Measure first.** Run the same 1 Hz probe that produced the existing fixtures, with Chrome in View ▸ Enter Full Screen and "Always Show Toolbar in Full Screen" on. Do it twice: with and without the bookmarks bar.
2. If the rect is full width, at x=0 and flush with the bottom, add a separate browser-toolbar allowance next to `MENU_BAR_MAX_PX` in `coversDisplayAllowingMenuBar`, sized from the measurement (about 160 to cover the bookmarks bar). Width, left edge and bottom stay exact.

**How it keeps "a maximised window is not fullscreen":**
- Safari maximised (`SAFARI_MAXIMISED`, `test/fullscreen.test.ts:270`, 1728×1018 at (0,33)) still fails on the bottom edge, because the Dock keeps it 66 px clear.
- Windows' maximised-overhang exclusion (`overhangsEveryEdge`, `:461`) is untouched.
- The existing tests at `test/fullscreen.test.ts:80`, `:281`, `:332` and the W6 block at `:733` must stay green. Add the new Chrome fixture plus a negative: a full-width, bottom-flush window whose top is just past the new limit.

**Risk:** moderate.
- It widens the false positive already accepted at `fullscreen.ts:477-484` (Dock hidden and maximised reads as fullscreen). Any full-width window flush with the bottom and up to about 160 px short at the top would now put him to sleep: a Dock-hidden maximised app whose window does not reach the menu bar, or a hand-sized window.
- The module is platform-neutral, so Windows is affected too. A window snapped there with a top band of 45–160 px is rare.
- Do not guess the constant without the measurement.

**On-screen check (Mac):**
1. In Chrome, View ▸ Always Show Toolbar in Full Screen on, then Enter Full Screen. Within about 3 s he curls up asleep.
2. Exit fullscreen: he wakes.
3. Maximise Safari with the Dock visible: he stays awake.
4. Repeat with the bookmarks bar on.
5. Repeat player fullscreen on YouTube (row 6.x): still sleeps.

## c) Petting the dog takes key focus from the window under him
**Still present on 0.3.0:** unknown, presumed yes, macOS only. On Windows `focusable: false` does not activate, and QA row 6.3 passes there (`docs/QA-CHECKLIST.md:207`).

**What 0.2.9 changed:** `a39b74b` touched only `src/core/fullscreen.ts`, `src/main/fullscreen-watch.ts` and `test/fullscreen.test.ts`. With Walder frontmost, `readFullscreen` returns `null`, so a pet no longer wakes him from a film. Its commit message confirms the underlying fault: "Electron's panel window still activates it". Nothing else has changed.

**Root cause (as recorded, not verified in code):**
- The overlay is `type: 'panel'` with `focusable: false` (`src/main/overlay-window.ts:452-455`).
- On macOS a mouse-down in it still makes Walder the active app, so the app under the dog loses key status.
- Electron has no flag here beyond `panel`. There is no `app.hide`, re-activation or similar code anywhere in `src/main`.

**Proposed fix (needs an on-screen experiment first; two options):**
1. **The sketched one** (`QA_0.2.8_REPORT.md:27`): call `app.hide()` after the click, macOS only, when Walder is frontmost. macOS then returns activation to the previous app. **Risk:** `app.hide()` hides all of Walder's windows, the overlay panel and the card included, so the dog may vanish. That is the whole open question, and why it is marked unverified.
2. **Safer:** remember the last non-Walder frontmost app. The fullscreen watch already polls it, with pid and path, through `get-windows`. After a pet, if Walder became frontmost and the dog is not "waiting" (petting a waiting dog raises the terminal on purpose, `c9f0d6d`), re-activate that app. That needs `open -b <bundle>` or `osascript … activate`. **Risk:** an Automation prompt, a short visible flicker of activation, and it must not race the waiting-dog raise.

**On-screen check (Mac):**
1. Type in TextEdit and leave the cursor blinking.
2. Pet the dog with one click.
3. Without clicking TextEdit, type again. Pass: the letters land in TextEdit, and TextEdit's title bar and the menu bar stay TextEdit's.
4. The dog stays visible and plays `pet`.
5. Repeat while the dog is "waiting": the terminal is raised, as designed.
6. Repeat over a fullscreen video: he stays asleep (row 6.3).

## d) Mac position fault 1: a size round trip at the top edge ends 144 pt lower
**Still present on 0.3.0:** yes (from the code). It is not Mac-only: the Windows report measured the same 144 px at 100 % and about 166 DIP at 125 % (`WINDOWS_AUDIT_2026-11_REPORT.md`, section 11 tables).

**Root cause:**
- `resize()` (`src/main/overlay-window.ts:899-954`) always keeps the window's **bottom**: `bottom = before.y + before.height` at `:908`, and `y: bottom - probe.height` at `:924`.
- Size changes have a horizontal anchor (`anchorRight`, `:917-919`, the X1 fix) but no vertical one.
- Stand box: 72×72 (`src/sprites/walder.json`). Scales: 1/2/3 (`src/main/ipc.ts:152-154`). The bubble reserve is above the ink and cancels out.
- At the top edge, with bottom B and ink top = area top T:
  - Small → Medium: the new ink top is B−144 < T, so the clamp pushes him down 72.
  - Medium → Large: down another 72.
  - Large → Small keeps the pushed bottom B+144, so the ink top is T+144.
  - This matches the measured 72 (via Medium) and 144.
- In the top half away from an edge nothing is clamped, so a round trip comes home. Only a dog whose growth hits the top is moved.

**Proposed fix:**
1. Mirror X1 vertically: an `anchorBottom` (or `anchorTop`) decided in `decideAnchor` (`:520-523`) from a new `onTopHalf(rect)`, next to `onRightHalf` (`:491`).
2. In `resize`, on the non-centred path, after the `anchorRight` line:
   ```ts
   if (anchorTop) bottom += metricsFor(nextScale,'stand',0).height - metricsFor(currentScale,'stand',0).height;
   ```
   This is zero for a box or bubble change, so sleep and bark still keep his feet. In the top half he then grows downwards, keeps the window's top edge, and comes home exactly.
3. Tests: the X1 round-trip tests in `test/overlay-window.test.ts` (search "audit X1" / "round trip"). Add a top-edge and top-left-corner Small→Medium→Large→Small case returning to the same rect, and keep the bottom-edge and home-corner cases unchanged.

**Risk:** low to moderate.
- A dog in the top half now grows down instead of up. That is visible behaviour, and it is the same trade the owner accepted for X1.
- The interplay with the 2026-11-17 top-edge bubble layout ("bubble below at a top edge") needs one look.
- Not persisted across relaunch, like `anchorRight`.

**On-screen check (Mac, then PC at 100 % and 125 %):**
1. Drag him flush to the top edge, mid-width, at Small.
2. Size ▸ Medium ▸ Large ▸ Small. Pass: he ends on the same pixel he started on, with no ink above the menu bar at any step.
3. Repeat in the top-left and top-right corners.
4. Repeat at home (bottom-right): unchanged, back on the pixel.

## e) Mac position fault 2: a 25 pt gap under the menu bar
**Still present on 0.3.0:** yes (from the code). Per the audit it is a design consequence, and the Windows report records it as a pass: "At rest the sprite frame is on the edge" (`WINDOWS_AUDIT_2026-11_REPORT.md:540`).

**Root cause:**
- The clamp measures the 72×72 **sprite frame** (the box), not his opaque pixels.
- `inkInset` (`src/core/geometry.ts:807-810`) is pad plus bubble reserve. `drawnInkInset` (`:903-927`) is the drawn box's edges.
- The frame has transparent margins. On Windows at 100 % they measure 3/7/3 sprite px (left/top/right), so 7/14/21 px of top margin at Small/Medium/Large.
- **I could not reproduce the Mac numbers** (25 pt top, 4 pt sides) from 7·scale and 3·scale at any single size: Large gives 21/9, Medium 14/6. Part of the 25 pt may be something else: the bubble reserve, the spriteFit/dpr layout, or a measurement artefact. Treat the cause as "frame, not ink" in principle, with the exact split unconfirmed.

**Proposed fix (clamp side only, never the art):**
1. Compute, once at sheet load (in `src/core`, from frame data, read-only), the union of opaque rows and columns over every frame each box can show.
2. Add that margin to `drawnInkInset`'s top, left and right, scaled with the layout.
3. Re-measure the gap on screen before and after to confirm it is this.

**Risk:** moderate.
- Every clamp, the start position and the saved-position migration move by a few points.
- Frames with ears or jumps reach into the margin, so a union narrower than every frame would push ink off screen. It must be the true union.
- `test/geometry.test.ts` has the whole inset table pinned (`geometry.ts:699`) and would all change.
- It also tightens bubble room at the top edge.
- The owner may prefer to accept the gap. The audit lists it as his call.

**On-screen check (Mac):**
1. At each size, drag him hard into the top edge.
2. Zoom a screenshot (Cmd-Shift-4). Pass: the highest opaque pixel of his head (ears up) touches the menu bar's bottom row, and the side pixels touch the screen edges.
3. Watch a full idle cycle (blink, wag, ears) at the edge: no pixel above the menu bar.

## f) The 125 % Windows drag fault: what is known
**Still present on 0.3.0:** yes (from the code). The drag still moves the window with `win.setPosition(held.x, held.y)` (`src/main/overlay-window.ts`, `dragMove` at `:1419`, the `setPosition` near `:1470`). The drag-grow patch is **not in the repo**: no `*.patch` file in the tree, nothing in `git stash` on the Mac, nothing in branch logs.

**Known (from `WINDOWS_AUDIT_2026-11_REPORT.md` §10.3, §11):**
- Seen at 125 % only. At 100 % the window size is stable over about 1000 readings per drag.
- A purely horizontal 250 px drag sank him 45 DIP and left the window oversized (210×244 DIP at Small).
- He also creeps 1–3 DIP per size change and 2 DIP per sleep/wake or bubble.
- The fault predates both fixes (the control on `b90aae4` was identical).
- Current code contains it rather than curing it:
  - `insideHeld` measures the largest window seen during the drag (`:543`), so after a long drag he can stop short of the top edge by everything the window has grown (46 DIP in a pinned test).
  - `resize` does one grant read-back and at most one `setPosition` (`:956-975`).
- **The written fix:** `patchesdrag-grow.patch`, on top of the inside-screen patch, in worktree `wt-inside` **on the owner's PC only** (gates 0/0/0 there, 3209 tests). Every move becomes one `setBounds` that restates the last-asked size, and `setPosition` is never called. That `setPosition` is the cause is explicitly "a guess until it is run at 125 %".
- The likely mechanism: Windows grants 1–2 DIP more than asked at fractional scale, and `setPosition` keeps the granted size each move.

**Proposed next step:**
1. On the PC, check whether the patch still applies to main.
2. If it does not, re-apply it by hand in `dragMove`: `win.setBounds({ ...held, width: currentMetrics.width, height: currentMetrics.height })`.
3. Run the gates, then test at 125 %.

**Risk:** low in code, unknown in effect. `setBounds` on every move may cost more on Windows. Measure smoothness.

**On-screen check (PC at 125 %):**
1. Size Small at home.
2. Drag 250 px straight left and release. Pass: the same y to the DIP, and the window still 88-ish wide (log or Spy++). No sink after five back-and-forth drags.
3. Drag into the top edge: he reaches it flush.
4. Size round trip at home: back on the pixel.

## g) Windows: can the hook confirm dialog slip behind other windows?
**Still present on 0.3.0:** yes (from the code).

**Root cause:**
- On Windows the dialog has no parent: `showMessageBoxWithoutBlocking` returns `dialog.showMessageBox(options)` for every non-darwin platform (`src/main/dialog-host.ts:67`).
- The macOS host window (`:69-94`) is an ordinary, non-always-on-top window, so it can sink too.
- `oneHookDialogAtATime` (`src/main/index.ts:845-857`) then silently drops any further hook click ("a hook dialog is already open; not opening another"), with nothing on screen.
- Also open from §5.2: `defaultId: 0` is Install/Remove (`index.ts:805`, `:940`), so a stray Enter acts.

**Proposed fix:**
1. Use the host window on Windows as well, with `host.setAlwaysOnTop(true, 'floating')` on both platforms, and pass it as the parent. The dialog is then owned by a topmost window and stays above.
2. Keep a module-level reference to the open host. When `hookDialogUp` is already set, call `host.show(); host.moveTop()` (or focus) instead of only logging, so a second click brings the lost question forward.
3. Separately, if Victor agrees, set `defaultId: 1` (Cancel).
4. Update `test/dialog-host.test.ts`. The current header (`dialog-host.ts:37-38`) says Windows passes through on purpose. Keep the non-blocking property: a parented async box on Windows is still non-blocking.

**Risk:** low to moderate.
- On Windows the transparent, frameless host would swallow clicks in its 520×420 area while it is up (a modal owner does anyway).
- An always-on-top question sits above fullscreen apps, which is arguably right for a question the owner asked for, but it is a behaviour change at the launch offer.

**On-screen check (PC, then Mac):**
1. Tray ▸ Install Claude hooks. The dialog shows.
2. Click another app (Explorer) to the front. Pass: the dialog stays visible above it.
3. Click Tray ▸ Install Codex hooks: the existing dialog comes to the front (no silent nothing).
4. Press Enter with the dialog focused: only if the default changed, it cancels, and the log shows `cancelled at the confirmation`.
